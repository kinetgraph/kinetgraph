## Context

The current `WorkerManager` dispatches every tool execution
through a single `ProcessPoolExecutor`, sized as
`max_workers = max(2, min(32, sum(max_concurrency)))`. This
model treats all tools the same: the same Python process is
spawned for each, the same `loop.run_in_executor` runs
`tool.invoke()`, and the result flows back through the same
I/O path.

This generic model breaks down for tools with heavy shared
dependencies (ML models holding 700 MB–1.5 GB in RAM). The
concrete case from the `backoffice`:

- `document_parser` (Docling 700 MB) and
  `document_text_extractor` (GLiNER 840 MB) share the same
  execution profile (CPU bound + ML) but are separate tools.
- Each pool worker imports torch + the tool module → ML
  model duplicated per worker.
- The `max_concurrency` semaphores are **per-tool**; heavy
  tools with independent semaphores can run in parallel,
  summing 1.5 GB of models simultaneously.

Today backoffice works around this with a fork
(`max_pool_workers=4` global), but the structural pattern —

> "tools with the same execution profile should be able to
> share a dedicated pool, without that becoming coupling in
> the framework"

— has no primitive. Backoffice has to choose between:
(a) rewriting the entire `WorkerManager` (high cost), or
(b) coupling every tool to the shared `ProcessPoolExecutor`
(unpredictable memory). Neither scales.

### Analogous problem in other services

The same pattern appears in any service with heterogeneous
tools:

- **Sync blocking tool** in an async service (legacy
  `boto3.client`, `subprocess.run`): needs
  `ThreadPoolExecutor` instead of `ProcessPoolExecutor`.
- **Tool with heavy GPU/ML deps** that wants to share
  process + model between invocations.
- **Tool with a sidecar dependency** that needs its own
  lifecycle (e.g., `start_embedded_browser()` before the
  first call).

Each of these is a different **execution strategy**. The
current primitive (the CPU-bound vs non-CPU-bound choice) is
binary and rigid.

---

## Decision

Add an optional `executor_factory` parameter to
`WorkerManager.register()`. When provided, it overrides the
internal `loop.run_in_executor(self._pool, ...)` with a call
to this factory. Tools registered without `executor_factory`
keep using the current path (zero breaking change).

### API

```python
# kntgraph/tools/manager.py

from collections.abc import Awaitable, Callable

# Callback signature:
# Receives: (sync_invoke_fn, idempotency_key, tool_params)
# Returns: coroutine that resolves with result_dict
#          ({"status": "ok"|"err", "value"|"error": ...})
ExecutorFactory = Callable[
    [Callable[[str, dict], dict], str, dict[str, Any]],
    Awaitable[dict[str, Any]],
]

class WorkerManager:

    def register(
        self,
        tool_cls: type,
        *,
        acl: ACL | None = None,
        executor_factory: ExecutorFactory | None = None,
    ) -> None:
        ...
        self._tools[tool_name] = tool_cls
        self._executors[tool_name] = executor_factory  # new dict
```

### Change in `_process_message`

```python
# kntgraph/tools/manager.py

executor_factory = self._executors.get(tool_name)
if executor_factory is not None:
    # Custom path: delegate execution. Manager still owns
    # XACK, events, metrics, ACL, observability.
    result_dict = await executor_factory(
        _invoke_tool_sync, idempotency_key, tool_params
    )
elif is_cpu:
    # Current path: shared ProcessPoolExecutor.
    result_dict = await loop.run_in_executor(
        self._pool, _invoke_tool_sync, tool_cls, idempotency_key, tool_params
    )
else:
    # Current path: async tool, runs in the loop.
    result = await tool_instance.invoke(idempotency_key=idempotency_key, **tool_params)
    result_dict = {"status": "ok" if result.is_ok() else "err", ...}
```

### Compatibility

- **Default `executor_factory=None`** → current behavior
  preserved bit-for-bit. No breaking change.
- Tools that don't pass the parameter see no difference.
- The opt-in custom dispatch is the caller's responsibility
  (at `register()` time); the framework does not enforce any
  strategy.

### What the framework does **NOT** do

- **Does not know about `ModelWorkerPool`, thread pools,
  sidecars, etc.** The factory is opaque — it receives a
  sync function and params, returns a `result_dict`. The
  framework treats it as a black box.
- **Does not dictate the executor's lifecycle.** The factory
  is called on each invocation; the caller owns starting
  and stopping the underlying executor.
- **Does not serialize/deserialize across processes.**
  That's already the responsibility of the internal
  `ProcessPoolExecutor`; custom factories reuse whatever the
  caller provides.

### Usage example (backoffice)

```python
# backoffice/infra/model_worker_pool.py

class ModelWorkerPool:
    """Singleton pool for tools with heavy ML deps."""

    def __init__(self, max_concurrency: int = 1) -> None:
        self._sem = asyncio.Semaphore(max_concurrency)
        self._executor: ProcessPoolExecutor | None = None
        self._tool_cls: type | None = None

    async def start(self) -> None:
        self._executor = ProcessPoolExecutor(
            max_workers=1,
            mp_context=multiprocessing.get_context("spawn"),
        )

    def as_executor_factory(self) -> ExecutorFactory:
        # Closure captures self._executor and self._tool_cls
        async def factory(_invoke_in_worker, idempotency_key, tool_params):
            async with self._sem:
                loop = asyncio.get_running_loop()
                return await loop.run_in_executor(
                    self._executor,
                    _invoke_in_worker,
                    self._tool_cls,
                    idempotency_key,
                    tool_params,
                )
        return factory

# backoffice/main.py

model_pool = ModelWorkerPool(max_concurrency=1)
await model_pool.start()

worker_manager = WorkerManager(
    redis=redis, event_log=log, group_name=..., key_prefix=...,
    max_pool_workers=4,
)

# Heavy tools: each points to the SAME pool (1 process,
# model loaded once). model_pool._tool_cls is set per tool
# at register time.
for tool_cls in [DocumentParser, DocumentTextExtractor]:
    model_pool._tool_cls = tool_cls
    worker_manager.register(
        tool_cls, acl=None, executor_factory=model_pool.as_executor_factory()
    )

# Light tools: stay on the framework's internal pool
for tool_cls in get_light_tools():
    worker_manager.register(tool_cls, acl=None)  # no factory
```

### What the Manager keeps doing (unchanged)

- **XREADGROUP** in the consumer loop
- **XACK** after success/error
- **Reaper** with `XAUTOCLAIM` (with the reaper-skip-semaphore
  fix — see ADR-013)
- **ACL check** (ADR-066 §4.1)
- **Metrics** (`messages_processed_total`, etc.)
- **Observability** (`worker.xack`, `worker.tool.hard_crash`, etc.)
- **Domain events** (`.completed` / `.failed` in the eventlog)

The primitive affects **only** the "how do I run `invoke()`"
point. The rest of the message lifecycle is preserved.

### Traceability: why the Redis `message_id` is NOT in the signature

The factory receives `(sync_fn, idempotency_key, tool_params)`.
Application-level traceability is guaranteed by the framework
IDs that **already** arrive through these parameters — no need
to expose the Redis Stream `message_id`:

| ID | How it reaches the factory | Use |
|---|---|---|
| `event_id` (= `ik`) | `idempotency_key` parameter | Log key, metric, trace point |
| `correlation_id` | `tool_params["correlation_id"]` | Group events in the same flow |
| `causation_id` | `tool_params["causation_id"]` | Causal chain: "this event was caused by that" |
| `agent_id` | `tool_params` (if the tool uses it) | Agent scope |

The wiring in `manager.py`:

```python
# line 582: ik is the event_id
idempotency_key = str(request_event.event_id)

# lines 649, 709, 720, 762: causation_id derived from ik
causation_id=uuid.UUID(idempotency_key)
```

The Redis `message_id` (e.g., `1791460835580-0`) is **just a
position in the stream** — relevant for XACK / XREADGROUP /
XAUTOCLAIM (transport operations), not for application
dispatch. If an operator needs to debug "where the message
is stuck in the stream", `XPENDING <stream> <group>` resolves
server-side without the ID needing to be in the factory.

**Consequence:** the current signature is sufficient for rich
factory-side observability. Extending the signature to
include `msg_id` would be speculative complexity (YAGNI) —
add only if a real caller asks for it.

## Alternatives considered

### A. Do nothing; caller implements its own `WorkerManager`

- **Pros:** zero framework change.
- **Cons:** ~800 lines rewritten; inconsistency between
  services; per-product decision.
- **Verdict:** rejected — the primitive is generic enough
  to belong in the framework.

### B. Add `executor_type: Literal["process", "thread", "inproc"]`

- **Pros:** enum instead of callback; more "typed".
- **Cons:** narrows the strategy space. Caller cannot do
  custom lifecycle (start/stop), GPU pinning, or sidecars.
- **Verdict:** rejected — the primitive needs to be
  extensible, not a closed enum.

### C. Accept `executor: ProcessPoolExecutor` (instance) instead of factory

- **Pros:** conceptually simpler.
- **Cons:** forces the caller to use `ProcessPoolExecutor` —
  those who want `ThreadPoolExecutor` or a sidecar are
  locked out. Couples the strategy to a concrete type.
- **Verdict:** rejected — loses generality.

### D. Accept `run_fn: Callable[..., Awaitable[Any]]` directly (no sync invoke)

- **Pros:** caller writes the whole function.
- **Cons:** changes the tool's invoke signature. Tools that
  are `async def invoke(...)` today would need to be
  adapted.
- **Verdict:** rejected — breaks the public tool API.

The chosen primitive (this ADR's option) is the only one
that:
- Doesn't break compatibility
- Doesn't force a concrete type
- Preserves the `async def invoke(...)` tool interface
- Is generic for future use cases (GPU pinning, thread
  pool, sidecar, etc.)

---

## Consequences

### Positive

- **Backoffice resolves ML OOM** with 1 process and
  shared model (vs. 13 processes today). Peak memory
  drops from ~3.5 GB to ~2.8 GB on Fargate 4 GB.
- **Other services get the same pattern** without rewriting
  `WorkerManager`. Examples: GPU-pinning tools, browser
  sidecars for Playwright tools, blocking-subprocess tools
  in async services.
- **Future extensibility:** if the framework wants to add
  `executor_type="thread"` as a convenience, it's a 5-line
  wrapper over this primitive.
- **Bit-for-bit compatibility:** tools registered without
  the parameter see no difference. Zero breaking change.

### Negative

- **Implicit coupling:** tools that use `executor_factory`
  depend on something outside the tool (the factory). The
  tool becomes "agnostic" but the caller needs to know
  which strategy to apply.
- **Partial observability:** the Manager still emits
  `worker.consume_loop.heartbeat`, `worker.xack`, etc.,
  but custom-pool metrics (latency, model load time)
  need to be emitted by the pool itself.
- **Two pools to manage:** caller has to `start()` /
  `stop()` both the `WorkerManager` and the
  `ModelWorkerPool` (or similar). Coordinated lifecycle.
- **Integration testing:** testing the pool + Manager
  integration requires bringing up the custom pool in the
  fixture. Not a big complication, but one more level.

---

## Residual risks

- **Factory exception not handled:** if the factory raises
  before calling `_invoke_in_worker`, the Manager doesn't
  know — the `try/except` in `_process_message` only
  covers the tool invocation, not the factory itself.
  **Mitigation:** document the contract ("factory must
  either be resilient or let the exception propagate") and
  add a `try/except` with structured log around the factory
  call.
- **Blocking async factory:** if the factory is `async def`
  but does blocking I/O, it stalls the Manager's event
  loop. **Mitigation:** document that an async factory
  must be pure `await` (no blocking I/O).
- **Pool size + factory interaction:** if
  `max_pool_workers=4` but a tool has a factory with 1
  internal worker, the Manager's pool count is
  inaccurate for metrics. **Mitigation:** document that
  `max_pool_workers` only counts internal pool workers;
  custom factories have their own sizing.

---

## Success metrics

1. **Stable API:** `register(executor_factory=...)` accepts
   `None` and the documented factory types; `pyright` /
   `ruff` clean.
2. **Compatibility:** the existing kinetgraph test suite
   continues to pass with no behavior change.
3. **Backoffice consumes the primitive:** the backoffice's
   ADR-014 marks the usage as "Accepted" and references
   this ADR as upstream.
4. **No OOM regression** on Fargate 4 GB after backoffice
   adopts (measured via `docker stats` during
   `uat/simulate.py` under sustained load).

## Implementation plan (~2-3h)

1. Add `executor_factory: ExecutorFactory | None = None`
   to `register()`. ~10 lines.
2. Add `self._executors: dict[str, ExecutorFactory] = {}`
   to `__init__`. ~1 line.
3. Extend `_process_message` to consult the factory before
   CPU/async dispatch. ~10 lines.
4. Type alias `ExecutorFactory` at the top of `manager.py`.
5. Docstring on `register()` explaining the contract.
   ~10 lines.
6. Update `docs/adr-068-operational.md` with a cross-
   reference to this ADR.
7. Add 1-2 integration tests that register a tool with a
   custom factory and validate that:
   - The factory is invoked with the correct args
   - The result comes back in the expected `result_dict`
     format
   - XACK still happens

## Reversal plan (~10 min)

The primitive is **opt-in**. If it causes trouble:

1. Revert the PR
2. Callers that used `executor_factory=` stop working
   (they need to remove the kwarg to fall back to the
   default path)

No side effects on code that does not use the primitive.
